## 2. Decisions taken in this re-plan

Each entry states what changed, why, and what earlier vault decision it overturns. All nine decisions were **confirmed by the founder on 2026-09-02**, including D1 and D2, which overturn earlier vault decisions.

**D1 — Ship free and open (MIT) first; monetize only after validation.**
Why: zero users, unproven demand, and a headline mechanism the founder's own ablation shows adds nothing yet. Every comparable that monetized (Smart Connections, Copilot for Obsidian, Basic Memory, Vestige, Khoj) started free. Overturns *Paid-From-Launch Monetization and Licensing Backend Decision* (2026-08-16). **Confirmed 2026-09-02.**

**D2 — If validated, monetize the Obsidian plugin "Pro" through a Merchant-of-Record platform with license keys; no owned billing backend.**
Why: a MoR (Polar, Lemon Squeezy, Paddle) costs ~5% + 0.50 per transaction and removes ~45 tickets (Stripe webhooks, entitlement DB, dunning, portal, VAT, hosting, secrets, monitoring). Self-building pays off only past ~2–3k subscribers. Price like the neighbours: 29–49 EUR/year or a capped 79–99 EUR lifetime "founding" tier, never 3.50/month (the 0.50 fixed fee makes that an 18% take). Overturns "no marketplace resellers / Stripe direct, user is MoR" (2026-08-16). **Confirmed 2026-09-02.**

**D3 — Reposition: lead with what is measured and visible.**
Headline becomes: *your vault is already a brain; VNL gives your agent working memory over it — ~~session priming~~, link-structure-aware retrieval, a live neural graph — and it travels with you from Claude Code to Codex to Gemini.* "Hebbian / gets better with use" moves to the roadmap and science story until Phase 2 measures a lift. Does not overturn any vault decision; the portability positioning (2026-08-16) stays.

**D3 amended 2026-09-09 (founder's decision, on VNL-058's measurement): session priming is struck from the headline and switched off in the serving path.** It scored +0.039 MRR in the target-primed condition and **−0.017 in the related-primed one** — that is, it helps when the session buffer already holds the note being searched for, which is the circular case the whole benchmark redesign exists to stop treating as evidence, and it *hurts* in the realistic one, where you have read around a subject and want the note you have not seen. In plain terms it made the engine repeat what you had already read, above what you were looking for. The mechanism stays implemented and reachable via `layers`, and `why.primed` still reports whether a hit was seen this session, because that is information about a result rather than a thumb on the scale. What replaces it in the headline is what did measure: **the briefing that reaches every session without being asked for** (VNL-064) is the concrete form of "working memory over your vault", and unlike priming it is delivered rather than inferred. Striking a mechanism from the pitch the same day its number came in is the point of D6, not an exception to it.

**D4 — Security and data-safety fixes precede the first publish.** Path containment, loopback socket, frontmatter preservation, compactor durability. These are hours of work each and are the difference between "alpha" and "unsafe". New decision.

**D5 — Retract the scale claim to what is measured; redesign the index before claiming anything above ~20k notes.** README and INSTALL say what was verified (search, synthetic 300k) and nothing more. Monolithic JSON indexes parsed per query are replaced by a SQLite-backed store in Phase 3. New decision.

**D6 — The benchmark is rebuilt before any quality claim is made publicly.** Unprimed and related-note-primed conditions, MRR alongside rank-1, ≥50 queries, a second vault, automated in CI. The current 18-query pre-seeded set stays as a regression test only. Extends AIBRAIN-66's "measure before adding mechanisms" (2026-08-15).

**D7 — Desktop app stays paused and off the critical path.** Confirms the 2026-08-30 pause; nothing in Phases 0–4 depends on it. Code stays in the monorepo.

**D8 — Jira is retired; this file is the backlog.** The vault stays the knowledge store. Per the founder's instruction, 2026-09-02. Jira project AIBRAIN is left untouched as a read-only archive; it can be archived or deleted by the founder at any time.

**D9 — Cold-start is a first-class problem.** The Hebbian layer cannot become informative from ~2 traversals/day. Phase 2 seeds initial weights from signals that already exist (backlink counts, file modification recency, optional Obsidian workspace history) and shortens the initial half-life, so the layer has a chance to earn its name by the month-6 gate. New decision.

**D10 — Engine usefulness thesis. Confirmed by the founder 2026-09-02, including the priority order of Phase 2b.**
The engine is not useful today for three structural reasons, none of which is a tuning problem: (1) its entry point is a *note* (`activate(note)`), but the agent's real question is a *query* ("what should I read for this task?"), so the graph never gets to improve a real search; (2) its only learning signal is the agent's own MCP traffic (~2 events/day), while the human's navigation inside Obsidian — 100x the volume — is ignored; (3) it ranks by graph and usage alone with no relevance model, so it can only re-rank things it was already pointed at. The fix is to make the engine a **query-driven hybrid retriever** in which lexical/semantic relevance answers *what matches*, the weighted graph answers *what this user actually uses together and what has gone stale*, and the Obsidian plugin becomes the primary **sensor**, not just a viewer. Work items: Phase 2b. This does not overturn any binding constraint: still MCP-only, no owned API key (embeddings run locally), deterministic logging, data stays in the vault.

| VNL-073 | **Outcome-gated link learning: links that learn whether they led somewhere useful.** Founder's direction 2026-09-28: the links should work like a brain, or like OSPF/EIGRP, where a link's weight is a *measured quality*, not a count of how often it was walked. Today's layer is plain Hebbian learning: co-access strengthens, nothing weakens except time, and popularity feeds itself. That shape is expected to be flat, and it measured flat five times. Missing pieces: a reward factor and active weakening. **(A) Log what was shown — ships with VNL-071, before anything else.** The `returned` line in `recall/*.jsonl` holds only `resultCount`, so no penalty can be computed and none of the 57 calls so far can be replayed. Add `hits: [{ path, rank, sources, seed?, via? }]`; it is additive, so old lines still parse. **(B) The fold** is a pure function beside `computeReadThrough`, run at compaction. Per call: a read result is +1, a read followed by a write or citation +2, and results ranked *above* the lowest read one but not opened are −1 (skip-above, the standard position-bias correction from click models). Results below the last read, and calls with no read at all, give **no** signal — the agent may have used the snippet, and treating that as failure would punish good results. Credit goes to the link that *delivered* the result: `seed → hit` for a graph hit (read from `why`), and `query-token → hit` otherwise (eligibility × reward, i.e. three-factor learning). **(C) The metric is a rate, not a count:** each link keeps decayed successes and failures in its own `outcome-weights.json` (never `link-weights.json`, same contamination rule as VNL-021/053). Its score is a Beta-smoothed success rate against a prior at the vault's own read rate (13% today), turned into a bounded log-odds shift. A link with no evidence scores exactly 0, and one read out of one is not 100% — so the rich-get-richer loop that sank priming cannot form, because frequency alone never raises a rate. **(D) Shadow mode:** `recall` computes the score and logs it per hit but blends it at weight 0, so nothing served changes until VNL-074 says it should. Not in scope: exploration (deliberately showing unproven results costs the user real sessions). **(A) done 2026-09-28:** `returned` lines carry `hits` (path, 1-based rank, source, score, every axis' score, `via`/`hops`, matched and learned terms) via a pure `toRecallLogHits`; old lines still fold, and an integration test drives it over the protocol. Logging starts when the MCP server restarts, and that date starts VNL-074's roughly 5-week clock. **(B–D) done 2026-09-28**, in `outcomeLearning.ts`, with two deliberate changes from the text above. (1) **No `outcome-weights.json`:** the model is derived on read from the `recall/*.jsonl` logs (a fold under 1 ms today, cached per process for a minute). A derived value cannot drift from or contaminate anything, and it doesn't depend on a nightly run that only happens while Obsidian is open. (2) **The shadow score is logged but never shown:** it goes on the log line as `outcomeScore` and is stripped from what `recall` returns to the model. A model that saw it might open high-scoring notes *because* of the score, and the experiment would end up measuring its own influence. Rules as designed: +1 opened, +2 opened in a call followed by a write, −1 skipped above the lowest opened result, silence below it and for calls with nothing opened. Credit goes to `note:seed|hit` and `term:word|hit` routes, and a result that arrived by meaning alone has no route. Each route's score is a rate smoothed toward the vault's own average (prior strength 2, 30-day half-life), expressed as a log-odds shift bounded at ±2 and undefined when there is no evidence. ## 9. Changelog

- **2026-09-28 (VNL-074 instrument built — the neural-links verdict now has a date and a rule)** — replay held out in time over the real recall log, with the weight fixed in advance (0.1), 100 held-out judged calls required, and a pass that needs more calls improved than worsened. It cannot run yet, because result lists have only been logged since today. The approximate smoke test on the 61 older calls points the right way (0.641 → 0.693, 5 up and 1 down), but it is not significant and not the gate. Rerun at roughly weekly intervals; at current use the gate becomes decidable in about 5 weeks (early November 2026), and the launch decision waits on it.

- **2026-09-28 (VNL-073 done, shadow mode)** — outcome-gated link learning is built and running in shadow. It is derived from the recall logs instead of stored, and hidden from the model so the experiment cannot steer itself. It changes nothing that is served. Its data accumulates from today; VNL-074 (the time-held-out replay) is next and decides whether it is ever switched on.

- **2026-09-28 (VNL-071 done, VNL-073(A) done)** — the semantic index is now kept current by the MCP server, which can load the model, not by the Obsidian plugin, which never could. One nightly step moved, not the pipeline: whether the rest of the nightly job should stay Obsidian-triggered is still open. Real-vault coverage went from 494/525 to 530/530. The gate margin over BM25 went from 0.060 to 0.071 on a fresh snapshot (0.692 vs 0.621). `recall` now logs the list it showed, so outcome learning (VNL-073 B–D) and the time-held-out benchmark (VNL-074) have their data from the next server restart on.

- **2026-09-28 (later — VNL-073/074 filed; the five flat readings were weaker evidence than stated)** — the founder asked whether real neural links, working the way a brain or OSPF/EIGRP does, are possible at all, or whether the idea is dead. Checking before answering found that the 70-query benchmark structurally cannot see usage learning: only 4 of 62 real reads touched a benchmark target. So the five readings show that learning does not help on questions it was never used for, which is not the same as the learning failing. They also fit what neuroscience predicts for Hebbian learning with no reward factor, which is exactly what is implemented. New direction, **founder-approved**: learning gated by outcome, with active weakening from skipped results, and a link metric that is a measured rate rather than an accumulated count (VNL-073, shadow mode). It is judged by a benchmark held out in time on the real logs (VNL-074), not by the fixed set. - **2026-09-09 (VNL-057 — the number the project steers by, in production)** — everything measured until now is measured against a benchmark, and VNL-020's is a good one, but its answers were chosen by a human who already knew what they wanted, it needs a maintained query set, and it cannot run on someone else's vault. Read-through can. When `recall` returns ten notes and the agent then opens one, that open is an unprompted judgement that the result was worth looking at — the same deterministic-signal discipline the project adopted after `reinforce_link` proved nobody calls a tool voluntarily (AIBRAIN-69). - **2026-09-09 (VNL-055 — the first thing here that does not wait to be asked)** — every retrieval path in this engine so far requires the model to decide, mid-task, that consulting the vault is worth a tool call. The project already knows how that goes: `reinforce_link` was invoked zero times in its entire life (AIBRAIN-69), which is why every learning signal since has been made deterministic rather than voluntary. The briefing applies the same lesson to retrieval — an MCP **resource** is offered by the server and attached by the client, so once attached its content arrives with no model decision involved, and resources are base protocol rather than a Claude extension, so it works on Codex and Gemini too (D3). **Correction, 2026-09-09, after the founder started a fresh session and found no briefing in it:** "attached by the client" describes the primitive's capability, not any client's default. Claude Code does not auto-inject MCP resources at session start — resources are reached by `@` mention and prompts appear as slash commands. The delivered-not-requested property therefore holds for the *model* (it chooses nothing once the resource is attached) and not for the *session* (a person or a hook still has to attach it). Automatic session-start delivery in Claude Code is a SessionStart hook, i.e. AIBRAIN-45, which this work leaves one thin CLI away. Shipped as `vault://briefing` (scoped from the working directory's name), a `vault://briefing/{project}` template, and a zero-argument prompt for a person who wants to *start* by catching up. The logic lives in `packages/core/src/briefing.ts` rather than the server, so AIBRAIN-45's SessionStart CLI can wrap the same code instead of duplicating a vault walk — the fix that note has been waiting for since 2026-07-26. Content is deliberately narrow, since a briefing that summarizes the vault is noise at the top of every session: what this project has been working with, what changed, what the link structure says is central, matching MOCs, and an inbox count. Project matching is exact-after-normalization (`vault-neural-link` → `Notes/VaultNeuralLinks`) and never fuzzy, because a briefing silently scoped to the wrong project is indistinguishable from a correct one to its reader — `matchedBy` says how it resolved, and an unmatched project says so instead of guessing. Superseded notes carry their successor, because a note in a briefing is read as current by virtue of being there. Two defects found by testing rather than by reading: the prompt declared an empty `argsSchema`, which makes the SDK demand an `arguments` object that no client sends for a zero-argument prompt, so **every real invocation would have failed with -32602** — caught only by driving a real MCP client over the transport, invisible to a unit test calling the handler; and against the real vault the briefing reported notes read minutes earlier as "last used 7 days ago", because usage weights only move when the nightly job folds the event log, so it now also reads uncompacted events (read-only, skipping `.compacting` files a live compactor has claimed, per-line failures swallowed like the compactor's own quarantine). 18 new tests; 382 core + 56 mcp-server green, all five packages typecheck, root build succeeds.

- **2026-09-09 (VNL-020 — the benchmark, and what it immediately found)** — the project can now tell "correct" from "primed". The old harness (AIBRAIN-31's `eval-retrieval.mjs`) started from an `(origin note, target note)` pair, called `activate(origin)`, and pre-touched the session buffer with the *target*, so it asked "does the note I already told the engine about rank first?" — and its distractor scored #1 for the same reason its real cases did. The replacement takes a **query**, runs it in three priming conditions (`unprimed`, `relatedPrimed` with a structural neighbour that is never the target, `targetPrimed` kept only as a regression), and reports MRR beside rank-1 against two baselines. It runs in two tiers: a 20-note fixture vault checked into `test/fixtures/` for CI (also the second corpus the plan asks for, with a deterministic topic-vector provider so the semantic axis is exercised without a model download), and a script against a real vault whose 70-query set is reviewed by hand and never checked in.

  **Result on the real 492-note vault, cold, empty session buffer: MRR 0.691, 40/70 rank-1, 68/70 found, against pure BM25's 0.616 / 35 / 62. The Phase 2b exit gate passes.** Two secondary numbers matter as much. `targetPrimed` reaches only 0.728, so cold retrieval is **95%** of primed retrieval — the circularity the 2026-09-02 audit found is genuinely gone, and the engine is not living off its own session buffer. `searchNotes` scores 0.044 (5/70 found), which is not a scalp: its all-tokens-present rule cannot answer a natural-language question at all, and no comparison against it should ever be quoted.

  **The decomposition is the real finding, and it reorders the roadmap.** Ablating one layer at a time, cold: full engine 0.691 / 40 rank-1 / 68 found; **without the semantic axis 0.602 / 33 / 63 — below plain BM25**; **without the graph axis 0.701 / 42 / 66**; without term learning 0.691 / 40 / 68, identical to three decimal places. So: (1) VNL-051's embeddings are the entire reason the gate passes, and the engine minus embeddings is *worse* than the BM25 it wraps; (2) the usage-weighted graph is **net negative on ranking** — removing it gains 0.010 MRR and two rank-1s — while adding two found notes, i.e. it widens recall and costs precision, which is the same shape as AIBRAIN-67's `zeroUsage` beating `asIs` and as the fixture's one-query regression; (3) term learning is inert at today's data volume, exactly as VNL-053 predicted it would be until the vault accumulates more. None of this is acted on here: re-tuning on the first run of a new benchmark is how the last set of unearned numbers happened. It goes to VNL-058 (mechanism diet) and VNL-022 (the month-6 gate on the usage layer), which now have evidence instead of an intention.

  **Founder reviewed and approved the query set the same day**, with no corrections, so 0.691 is a defensible measurement rather than a self-graded exam. Two caveats survive that approval: it is **one corpus** — the graph-axis finding needs ≥3 vaults before anything is removed on the strength of it — and it licenses nothing about scale (D5). The number also cannot be inflated by usage weights warmed during the session that produced it, since removing the graph axis entirely *raises* the score. Note for anyone reading the two query sets: the 70-query real set is used only by `scripts/benchmark-recall.mjs`; CI runs a separate 20-query set against the synthetic fixture and never touches a real vault. 364 core + 51 mcp-server tests green.

- **2026-09-09 (VNL-061, same day as the VNL-051 it completes)** — semantic hits now seed spreading activation. Until this, the graph phase drew its origins from the lexical top-N alone, which meant that on a query whose words appear nowhere in the vault — the one case the semantic axis exists for — there were no seeds and the graph contributed nothing: the two mechanisms ran side by side instead of compounding. Up to two semantic hits now become origins too. Energy allocation had to change to make that meaningful: BM25 is unbounded while cosine against real notes occupies a narrow 0.19-0.46 band, so a seed's share is now its score relative to the best on *its own* axis, with semantic strengths discounted by `semanticWeight` — the same discount the blend applies, for the same reason. Because each axis is normalized against its own maximum, a query with no semantic seeds distributes energy exactly as it did before, so this is a pure addition rather than a re-tuning. One labelling defect fell out of it and is fixed: a semantic seed self-activates, so it always carries graph energy now, and the existing source order would have labelled every meaning-found note `"graph"` — crediting the mechanism that echoed the find to the mechanism that made it. Semantic is checked before graph. Measured live on the real 494-note vault, and the result is genuinely two-sided: on "making the graph learn faster when there is not much data yet" the two correct notes went #4→#2 and absent→#5, each surfacing the other `via` the graph; on "how do we stop the assistant making things up" an unrelated UI note with the query's second-highest cosine (0.447) was amplified into the top 5. Semantic seeding magnifies the semantic axis in both directions, which is a VNL-020 question, not a tuning one. 4 new tests; 355 core + 51 mcp-server green, all five packages typecheck, root build succeeds. Noted in passing: `compactorDurability.test.ts`'s two-concurrent-compactions case failed once under the full parallel suite and has not reproduced in five subsequent runs or in isolation — recorded rather than chased, since nothing in this change touches the compactor.

- **2026-09-09 (VNL-051 correction, measured live)** — the semantic axis shipped in the morning with a fixed cosine floor of 0.35 and a comment claiming cosine is "bounded and comparable across queries, so it is not normalized". Running it against the real 494-note vault the same day showed that reasoning holds only for *symmetric* comparisons: two short paraphrases score 0.64, but a short question against a note's 1200-character opening puts every result — correct and incorrect alike — between **0.19 and 0.46**. At a 0.35 floor, two of four real queries admitted nothing at all and the feature was silently inert. What actually identifies the right note is its distance above the rest of its own distribution: on "paying for the product" the correct note scored 0.446 against a runner-up of 0.244, a separation no single absolute threshold can see. So the floor drops to 0.2 as a pure noise guard and a **relative cut** (0.6 of this query's best cosine, `semanticRelativeCut`) becomes the filter doing the real work. Verified live: the query that previously returned nothing now surfaces the note about signal starvation. Two further findings recorded rather than acted on, both for VNL-020 to settle: (1) with cosines capped near 0.46, `semanticWeight` 0.6 means a maximum contribution of ~0.28 against a lexical axis normalized to 1.0 — the semantic axis is currently a tie-breaker, not a retriever, and a note found on meaning alone essentially cannot outrank a mid-tier text match; (2) the compression itself is a symptom of embedding whole notes rather than passages (VNL-062). Also this day: `vnl-embed` CLI, because the nightly job runs on Obsidian's main thread and a first full build is 17.7s of CPU for 494 notes at ~28 notes/second (a measurement that corrected INSTALL's guess by an order of magnitude). Model load 2.4s; index 1.07 MB; incremental re-run embeds 0. 351 core + 51 mcp-server tests green.

- **2026-09-09 (Phase 2b, fifth item)** — VNL-051 `done`: optional local embeddings, so retrieval can match meaning and not only vocabulary. Until now nothing in the engine could reach a note that says the same thing in different words the *first* time: BM25 needs a shared token, the graph can only re-rank what something else pointed at, and VNL-053's term learning needs the association to already exist. The nightly job now embeds each note locally (all-MiniLM-L6-v2, ONNX, CPU) and `recall` blends cosine similarity in as a fourth axis at `semanticWeight` 0.6 — above the graph (0.5) and term (0.4) axes because, unlike them, it is a relevance model that works on a query it has never seen, and below lexical because a 384-dimension embedding of a note's opening 1200 characters is a lossy summary that happily calls two different project notes similar. It is the one axis **not** normalized against the best value in the result set: cosine is already bounded and comparable across queries, and normalizing would promote the best of a uniformly poor set to full strength — a floor (0.35) plus the absolute score is the point. Three shapes worth recording. **The model is an optional peer dependency**, dynamically imported: `onnxruntime-node` is a ~100 MB native binary and core has had zero runtime dependencies, so a hard dependency would put that in front of every `npx` install for a feature that is off by default; absent, unloadable, or throwing, every path returns "no semantic axis" and ranking is exactly what it was. **The nightly gate is tri-state** — `true` creates the index, `false` never does, and the default refreshes one that already exists — so a vault opts in once from the plugin's settings and stays current without the flag being threaded through every later call. **The index is incremental by content hash, not mtime**, because a synced vault rewrites mtimes without changing text and re-embedding a whole vault on every sync is the expensive mistake. Two defects found by the tests and fixed in the code rather than the assertions: a mangled base64 payload can decode to a plausible-length buffer, so a wrong-dimension vector is now excluded by dimension rather than scored 0 (which a floor of 0 still admits, letting a corrupt entry take a real result's slot); and `Buffer.from(base64)` can return an unaligned pooled slice, so decoding copies rather than views. Disclosed in README/INSTALL as what it is: the project's only network call, once, for the model download — note text never leaves the machine. No quality claim attached; VNL-020 is where the blend weights get earned (D6). 29 new tests; 347 core + 51 mcp-server tests green, all five packages typecheck, root build succeeds.

- **2026-09-04 (Phase 2b, out of order)** — VNL-060 `done`: `update_note` can now change frontmatter a key at a time, so an agent can finally mark a note superseded — the one "this note is outdated" signal `recall` already surfaces, and which until now only a human editing Obsidian by hand could write. The implementation edits the raw frontmatter block line by line rather than patching the parsed object and re-serializing it, because re-serializing is exactly what VNL-003 was fixed to stop: the minimal writer in `frontmatter.ts` cannot reproduce comments, key order, block-sequence style, or any YAML it does not parse, and a note that survived a body-only edit must survive a frontmatter edit too. - **2026-09-04 (Phase 2b, fourth item)** — VNL-054 `done`: the "Referenced" write-back signal. AIBRAIN-134's taxonomy says an MCP server cannot know which retrieved notes a model's answer actually used, because the protocol never shows the server that answer — true, and the reason true attribution is filed behind a model-API gateway. But there is one case it *can* see: the agent read note X this session and then wrote `[[X]]` into a note of its own. That is a citation in the tool call itself, needing neither a gateway nor a voluntary "I used this" tool call of the kind `reinforce_link` proved agents never make. It now logs a `reinforce` at 1.5 with `trigger: "cited"` — above auto-retrieval's 1, because reading a result only shows the agent looked, while citing it shows the note reached the work product; not above the old explicit boost, because AIBRAIN-66 measured how little it takes for oversized boosts to pin an arbitrary note at rank 1. Three deliberate narrowings: only notes actually **read** this session are candidates (a link to a note the agent never opened is structure, which the structural graph already covers), only the text supplied in *this* call is scanned (`writeNoteWithAutoLink` appends its own "Related (auto-linked)" wikilinks afterwards, and crediting machine-generated links as agent reasoning would be exactly the fetched-vs-useful conflation this ticket exists to avoid), and each note pair is credited once per session however often the note is rewritten. A bare `[[Title]]` resolves only when unambiguous among the notes read, mirroring `buildStructuralIndex`. - **2026-09-03 (Phase 2b, second item)** — VNL-052 `done`: the Obsidian plugin is now the engine's primary sensor. Two consecutive note opens within 10 minutes log a `traverse` at weight 0.25 (`trigger: "human-open"`); editing the note you navigated to logs a `reinforce` at 0.5 (`trigger: "human-edit"`), both far below an agent traversal's 1 because the human generates on the order of 100x the events and at parity the graph would become a heat map of clicks.
