## 2. Decisions taken in this re-plan

Each entry states what changed, why, and what earlier vault decision it overturns. All nine decisions were **confirmed by the founder on 2026-09-02**, including D1 and D2, which overturn earlier vault decisions.

**D1 — Ship free and open (MIT) first; monetize only after validation.**
Why: zero users, unproven demand, and a headline mechanism the founder's own ablation shows adds nothing yet. Every comparable that monetized (Smart Connections, Copilot for Obsidian, Basic Memory, Vestige, Khoj) started free. Overturns *Paid-From-Launch Monetization and Licensing Backend Decision* (2026-08-16). **Confirmed 2026-09-02.**

**D2 — If validated, monetize the Obsidian plugin "Pro" through a Merchant-of-Record platform with license keys; no owned billing backend.**
Why: a MoR (Polar, Lemon Squeezy, Paddle) costs ~5% + 0.50 per transaction and removes ~45 tickets (Stripe webhooks, entitlement DB, dunning, portal, VAT, hosting, secrets, monitoring). Self-building pays off only past ~2–3k subscribers. Price like the neighbours: 29–49 EUR/year or a capped 79–99 EUR lifetime "founding" tier, never 3.50/month (the 0.50 fixed fee makes that an 18% take). Overturns "no marketplace resellers / Stripe direct, user is MoR" (2026-08-16). **Confirmed 2026-09-02.**

**D3 — Reposition: lead with what is measured and visible.**
Headline becomes: *your vault is already a brain; VNL gives your agent working memory over it — session priming, link-structure-aware retrieval, a live neural graph — and it travels with you from Claude Code to Codex to Gemini.* "Hebbian / gets better with use" moves to the roadmap and science story until Phase 2 measures a lift. Does not overturn any vault decision; the portability positioning (2026-08-16) stays.

**D4 — Security and data-safety fixes precede the first publish.** Path containment, loopback socket, frontmatter preservation, compactor durability. These are hours of work each and are the difference between "alpha" and "unsafe". New decision.

**D5 — Retract the scale claim to what is measured; redesign the index before claiming anything above ~20k notes.** README and INSTALL say what was verified (search, synthetic 300k) and nothing more. Monolithic JSON indexes parsed per query are replaced by a SQLite-backed store in Phase 3. New decision.

**D6 — The benchmark is rebuilt before any quality claim is made publicly.** Unprimed and related-note-primed conditions, MRR alongside rank-1, ≥50 queries, a second vault, automated in CI. The current 18-query pre-seeded set stays as a regression test only. Extends AIBRAIN-66's "measure before adding mechanisms" (2026-08-15).

**D7 — Desktop app stays paused and off the critical path.** Confirms the 2026-08-30 pause; nothing in Phases 0–4 depends on it. Code stays in the monorepo.

**D8 — Jira is retired; this file is the backlog.** The vault stays the knowledge store. Per the founder's instruction, 2026-09-02. Jira project AIBRAIN is left untouched as a read-only archive; it can be archived or deleted by the founder at any time.

**D9 — Cold-start is a first-class problem.** The Hebbian layer cannot become informative from ~2 traversals/day. Phase 2 seeds initial weights from signals that already exist (backlink counts, file modification recency, optional Obsidian workspace history) and shortens the initial half-life, so the layer has a chance to earn its name by the month-6 gate. New decision.

**D10 — Engine usefulness thesis. Confirmed by the founder 2026-09-02, including the priority order of Phase 2b.**
The engine is not useful today for three structural reasons, none of which is a tuning problem: (1) its entry point is a *note* (`activate(note)`), but the agent's real question is a *query* ("what should I read for this task?"), so the graph never gets to improve a real search; (2) its only learning signal is the agent's own MCP traffic (~2 events/day), while the human's navigation inside Obsidian — 100x the volume — is ignored; (3) it ranks by graph and usage alone with no relevance model, so it can only re-rank things it was already pointed at. The fix is to make the engine a **query-driven hybrid retriever** in which lexical/semantic relevance answers *what matches*, the weighted graph answers *what this user actually uses together and what has gone stale*, and the Obsidian plugin becomes the primary **sensor**, not just a viewer. Work items: Phase 2b. This does not overturn any binding constraint: still MCP-only, no owned API key (embeddings run locally), deterministic logging, data stays in the vault.

## 4. Gaps found and proposals

Numbered so they can be referenced. Effort is engineering time.

1. **Path traversal (critical, 4 h)** — see VNL-001. Prompt-injected note content can currently make the agent read any `.md` on disk or write to any `.md` path. Must ship before publish.
2. **Frontmatter destruction (critical, 4 h)** — see VNL-003. Any vault not authored solely by this tool loses block-list aliases/tags on the first `update_note`. Must ship before publish.
3. **Open WebSocket (high, 1 h)** — see VNL-002.
4. **Event loss during compaction (high, 1 day)** — see VNL-004. The comment in `compactor.ts` claiming live files are left alone is false; they are in the processed set.
5. **Benchmark circularity (high, 2 days)** — see VNL-020. The current numbers cannot support any public claim; a skeptical reader will ask for exactly this ablation.
6. **Index scaling (high, 1 week)** — see VNL-031. Monolithic JSON parsed per query is the wrong shape; SQLite is the standard answer and keeps the local-files promise.
7. **Per-call I/O in retrieval (high, 1 day)** — see VNL-030. Cheap and large win.
8. **Cold start (medium, 2 days)** — see VNL-021. Without it the differentiator can never be tested fairly.
9. **Billing plan mismatch (strategic)** — D1/D2. Removes 25 tickets and 3–5 months of non-product work.

11. **Obsidian store rejection risks (medium, 4 h)** — AIBRAIN-43 as rescoped.
12. **No tests on 4,200 LOC** (plugin, render-core, desktop) — add vitest for render-core's pure functions (`orderClustersByConnection`, `computeClusters`) and one plugin smoke test; Windows job in CI. 1 day.

- **2026-09-09 (VNL-057 — the number the project steers by, in production)** — everything measured until now is measured against a benchmark, and VNL-020's is a good one, but its answers were chosen by a human who already knew what they wanted, it needs a maintained query set, and it cannot run on someone else's vault. Read-through can. When `recall` returns ten notes and the agent then opens one, that open is an unprompted judgement that the result was worth looking at — the same deterministic-signal discipline the project adopted after `reinforce_link` proved nobody calls a tool voluntarily (AIBRAIN-69). A `recall/*.jsonl` log records one `returned` line per call and attributes later `read` and `write` lines back to it; `computeReadThrough` folds them, and the plugin's Usage Report panel gets a "Was it useful?" section placed **above** the mechanism counts, because everything below it is diagnostics for why that number is what it is. Three deliberate choices. **Two rates, not one**: "read-through rate" can mean *opened / returned* or *calls where anything was opened*, and those differ by an order of magnitude at topK 10 — an agent served perfectly still scores 0.2 on the first. Picking one silently would have decided the Phase 2b exit gate by accident, so both are reported and **the gate's wording needs settling before it is judged** (the row reads "≥50% of recall results returned are subsequently read", which is the strict reading and is close to unreachable; the intended reading is more likely the second). **Writes stay separate** from reads rather than folded into a single usefulness number, because "opened" and "reached the work" are different claims and conflating them is precisely what AIBRAIN-134's evidence-state taxonomy exists to prevent. **Null, never zero**, before anything is measured: a rate of 0 reads as "nothing is ever useful", when the truth is "not measured yet". Attribution rules that keep the number honest: a read is credited to the most recent recall that returned it and only once (the same physical read counted against several calls would inflate the rate), a write counts once per recall (a session writing five notes after one useful recall did not have five useful recalls), reads whose recall is missing from a pruned log are dropped rather than adding to a numerator with no denominator, and results-read is capped at results-returned so a mangled log cannot produce a rate above 1. The new log is pruned on the same 90-day retention as `retrieval/` and `search/`. 13 new tests; 406 core + 61 mcp-server green, all five packages typecheck.

- **2026-09-09 (VNL-051 correction, measured live)** — the semantic axis shipped in the morning with a fixed cosine floor of 0.35 and a comment claiming cosine is "bounded and comparable across queries, so it is not normalized". So the floor drops to 0.2 as a pure noise guard and a **relative cut** (0.6 of this query's best cosine, `semanticRelativeCut`) becomes the filter doing the real work. Verified live: the query that previously returned nothing now surfaces the note about signal starvation. Two further findings recorded rather than acted on, both for VNL-020 to settle: (1) with cosines capped near 0.46, `semanticWeight` 0.6 means a maximum contribution of ~0.28 against a lexical axis normalized to 1.0 — the semantic axis is currently a tie-breaker, not a retriever, and a note found on meaning alone essentially cannot outrank a mid-tier text match; (2) the compression itself is a symptom of embedding whole notes rather than passages (VNL-062). Also this day: `vnl-embed` CLI, because the nightly job runs on Obsidian's main thread and a first full build is 17.7s of CPU for 494 notes at ~28 notes/second (a measurement that corrected INSTALL's guess by an order of magnitude). Model load 2.4s; index 1.07 MB; incremental re-run embeds 0. 351 core + 51 mcp-server tests green.

- **2026-09-09 (Phase 2b, fifth item)** — VNL-051 `done`: optional local embeddings, so retrieval can match meaning and not only vocabulary. Until now nothing in the engine could reach a note that says the same thing in different words the *first* time: BM25 needs a shared token, the graph can only re-rank what something else pointed at, and VNL-053's term learning needs the association to already exist. The nightly job now embeds each note locally (all-MiniLM-L6-v2, ONNX, CPU) and `recall` blends cosine similarity in as a fourth axis at `semanticWeight` 0.6 — above the graph (0.5) and term (0.4) axes because, unlike them, it is a relevance model that works on a query it has never seen, and below lexical because a 384-dimension embedding of a note's opening 1200 characters is a lossy summary that happily calls two different project notes similar. It is the one axis **not** normalized against the best value in the result set: cosine is already bounded and comparable across queries, and normalizing would promote the best of a uniformly poor set to full strength — a floor (0.35) plus the absolute score is the point. Three shapes worth recording. **The model is an optional peer dependency**, dynamically imported: `onnxruntime-node` is a ~100 MB native binary and core has had zero runtime dependencies, so a hard dependency would put that in front of every `npx` install for a feature that is off by default; absent, unloadable, or throwing, every path returns "no semantic axis" and ranking is exactly what it was. **The nightly gate is tri-state** — `true` creates the index, `false` never does, and the default refreshes one that already exists — so a vault opts in once from the plugin's settings and stays current without the flag being threaded through every later call. **The index is incremental by content hash, not mtime**, because a synced vault rewrites mtimes without changing text and re-embedding a whole vault on every sync is the expensive mistake. Two defects found by the tests and fixed in the code rather than the assertions: a mangled base64 payload can decode to a plausible-length buffer, so a wrong-dimension vector is now excluded by dimension rather than scored 0 (which a floor of 0 still admits, letting a corrupt entry take a real result's slot); and `Buffer.from(base64)` can return an unaligned pooled slice, so decoding copies rather than views. Disclosed in README/INSTALL as what it is: the project's only network call, once, for the model download — note text never leaves the machine. No quality claim attached; VNL-020 is where the blend weights get earned (D6). 29 new tests; 347 core + 51 mcp-server tests green, all five packages typecheck, root build succeeds.

- **2026-09-04 (Phase 2b, out of order)** — VNL-060 `done`: `update_note` can now change frontmatter a key at a time, so an agent can finally mark a note superseded — the one "this note is outdated" signal `recall` already surfaces, and which until now only a human editing Obsidian by hand could write. The implementation edits the raw frontmatter block line by line rather than patching the parsed object and re-serializing it, because re-serializing is exactly what VNL-003 was fixed to stop: the minimal writer in `frontmatter.ts` cannot reproduce comments, key order, block-sequence style, or any YAML it does not parse, and a note that survived a body-only edit must survive a frontmatter edit too. Only the lines of the named keys move; a `null` removes a key with its indented block; an array replacing a block sequence stays a block sequence rather than flipping to inline. One deliberate hard failure: a value containing a line break is refused with a message the model can act on, because this writer has no block-scalar syntax and the caller is now an LLM — a silently mangled frontmatter block is the kind of corruption a user would not notice for weeks. Found while writing the tests: a comment line between two keys was being swallowed into the preceding key's span and deleted on replacement — a span now ends at its key's last content line, with a regression test. 12 new tests; 313 core + 51 mcp-server tests green, all five packages typecheck, root build and the plugin bundle build.

- **2026-09-04 (Phase 2b, fourth item)** — VNL-054 `done`: the "Referenced" write-back signal. AIBRAIN-134's taxonomy says an MCP server cannot know which retrieved notes a model's answer actually used, because the protocol never shows the server that answer — true, and the reason true attribution is filed behind a model-API gateway. But there is one case it *can* see: the agent read note X this session and then wrote `[[X]]` into a note of its own. That is a citation in the tool call itself, needing neither a gateway nor a voluntary "I used this" tool call of the kind `reinforce_link` proved agents never make. It now logs a `reinforce` at 1.5 with `trigger: "cited"` — above auto-retrieval's 1, because reading a result only shows the agent looked, while citing it shows the note reached the work product; not above the old explicit boost, because AIBRAIN-66 measured how little it takes for oversized boosts to pin an arbitrary note at rank 1. Three deliberate narrowings: only notes actually **read** this session are candidates (a link to a note the agent never opened is structure, which the structural graph already covers), only the text supplied in *this* call is scanned (`writeNoteWithAutoLink` appends its own "Related (auto-linked)" wikilinks afterwards, and crediting machine-generated links as agent reasoning would be exactly the fetched-vs-useful conflation this ticket exists to avoid), and each note pair is credited once per session however often the note is rewritten. A bare `[[Title]]` resolves only when unambiguous among the notes read, mirroring `buildStructuralIndex`. Found while wiring the report: the plugin's Usage Report panel never got VNL-053's `termLearn` line despite that entry claiming it — added here alongside the new `cited` count. 8 new core tests, 3 new mcp-server tests; 301 core + 49 mcp-server tests green, all five packages typecheck, root build and the plugin bundle build.

- **2026-09-03 (Phase 2b, third item)** — VNL-053 `done`: term-to-note learning. Search queries were already logged, but the query itself — the fact that for *this* user "kill process by port" means one specific note — was thrown away; no static ranking can know that. `search_notes`/`recall` now queue credit for whichever of their hits gets actually read next (same retrieval-then-read lifecycle as AUTO_REINFORCE_BOOST), and that read persists a `query-token → note` edge per selective term into a new `term-weights.json`. Kept as a separate file from `link-weights.json` on purpose: a token is not a note, and letting one appear as a graph neighbor would let spreading activation walk into a shared word and back out into every note that ever matched it. The compactor's fold arithmetic is now shared between the two graphs rather than duplicated. `recall` blends live-decayed term scores into its ranking at `termWeight` 0.4 — below `graphWeight`'s 0.5, since a learned personal association is real evidence but easily stale and must not override what the query's words plainly say today — and adds a `"term"` source label for a hit that surfaces on that association alone, no text or graph link at all. Caught in the same pass: term events were leaking into `computeUsageReport`'s `topTouchedNotes`, keyed by the query token instead of a note path, because the touch-count loop ran unconditionally over every event type; term events are now counted on their own axis (`mechanismCounts.termLearn`) and excluded from touch counts, with a regression test. - **2026-09-03 (Phase 2b, second item)** — VNL-052 `done`: the Obsidian plugin is now the engine's primary sensor. Two consecutive note opens within 10 minutes log a `traverse` at weight 0.25 (`trigger: "human-open"`); editing the note you navigated to logs a `reinforce` at 0.5 (`trigger: "human-edit"`), both far below an agent traversal's 1 because the human generates on the order of 100x the events and at parity the graph would become a heat map of clicks. Written to the same `events/*.jsonl` log the MCP server uses, so compaction, decay and consolidation needed no changes at all; the usage report counts human signal on its own axis so it can't be mistaken for agent traffic. Guards against counting writes the user didn't make: an edit is credited only for the currently-open note and only while the Obsidian window has focus, since the MCP server's own `create_note`/`update_note` and any file-sync client fire Obsidian's `modify` event exactly like a keystroke does. Per-edge throttles (60 s for opens, 5 min for edits) keep flipping between two notes, or saving repeatedly while writing, from counting as many relationships. The decision logic lives in core's `HumanNavigationTracker` so it is unit-testable — the plugin class is a thin Obsidian adapter — which is also the first test coverage in this repo for plugin behaviour (gap #12). Default **on**, with a settings toggle and a README disclosure: it records note paths and timestamps to a folder inside the user's own vault, never any content and never over the network, so it does not touch the opt-in rule in the telemetry decision (that governs phoning home). 288 core + 43 mcp-server tests green, all five packages typecheck, plugin bundle builds.

- **2026-09-03 (Phase 2b starts)** — VNL-050 `done`: the `recall` tool ships, so the engine's entry point is a *query*, not a note (D10). Lexical relevance (BM25; document frequencies come free from the existing content index, term frequencies are computed live over a capped candidate set — the index carries no per-note counts and giving it some belongs to VNL-031, not here) picks the seed set; spreading activation runs per seed with energy proportional to that seed's share of the lexical score; both axes are normalized within the result set and blended at `graphWeight` 0.5, so the graph re-ranks and expands but cannot outrank a strong textual match.
