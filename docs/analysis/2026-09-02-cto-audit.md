## 2. Architecture assessment

### Data model — sound in shape, fragile in operation

All derived state lives in `<vault>/.vault-neural-links/`: `events/{instance}.jsonl` (append-only), `link-weights.json` (compacted), `structural-links.json`, `content-index.json`, `note-importance.json`, `note-clusters.json`, `session/{instance}.json`, `retrieval/`, `search/`, `activation-sockets/`. Every JSON writer uses tmp+`rename` (`compactor.ts:160-162`, `structuralLinks.ts:85-87`, `contentIndex.ts:187-193`, `importance.ts:88-90`, `clustering.ts:277-279`, `consolidation.ts:69-71`). Good.

Where it is fragile:

1. **Compaction loses events under concurrency.** `compactor.ts:75` reads all `events/*.jsonl`, then `:166-172` unlinks *every file it read*, including the live file of a running MCP instance. Any line appended by that instance between `readFile` and `unlink` is silently lost. The comment at `:164-165` ("any .jsonl written concurrently by a live session is left for the next run") is false — the file for a live session is in `processedFiles`. Two compactors running at once (Obsidian nightly + `compact_weights` tool, or two Obsidian windows) can also double-fold the same events into `baseStrength` (A reads events+weights, writes weights; B started after A's write but before A's unlink, reads the same events again on top of A's output). No lock, no test.
2. **One malformed line kills compaction forever.** `compactor.ts:48` `JSON.parse(trimmed)` with no try/catch. A crash mid-`appendFile` leaves a partial last line; every subsequent `compact()` (including the nightly) throws. `usageReport.ts:188-192` handles exactly this case — the compactor doesn't.
3. **Cloud sync is hostile to this layout.** The design note ("vault syncs across machines") is contradicted by the observed `*-Raptor1.json` OneDrive conflict copies in the real data dir. tmp+rename protects against partial reads on one machine, not against two machines each rewriting `link-weights.json`. There is no merge strategy; whichever machine syncs last wins and the other's fold is lost.
4. **Unbounded file growth.** `session/`, `retrieval/`, `search/`, `activation-sockets/` files are per-instance and never pruned (84 stale session files already; `index.ts:38-43` SIGINT handler only closes the socket). `priming.ts:376-379` documents the leak instead of fixing it.
5. `changelog.ts:578` `appendFile` to `changes.jsonl` has no write queue, unlike `logger.ts:205-214` — concurrent `create_note` calls from two sessions can interleave.

### Retrieval pipeline — correct but O(E) per call and I/O-heavy

`search_notes` → `notes.ts:244` `searchNotes` (index-narrowed text scan, then up to 500 `getWeightedNeighbors` calls for tie-breaking) ; `get_weighted_neighbors`/`activate` → `query.ts:363` `computeLiveNeighborWeights` → `activation.ts:109` `activate` → `fallback.ts:249` `retrieveWithFallback`.

- `computeLiveNeighborWeights` **re-reads `link-weights.json`, `note-importance.json`, and `structural-links.json` from disk on every call** (`query.ts:372,373,415`) and **scans every edge in the file** to find a note's neighbors (`:398-405`, O(E) `key.split("|")`). It also does a **file read per candidate neighbor** for `readNoteType` (`:402 → :296`). `activate` calls this once per visited node per hop, and `retrieveWithFallback` may call `activate` up to 4 times. `searchNotes` calls it up to 500 times per query (`notes.ts:338-347`) — the AIBRAIN-132 EMFILE/OOM incident was a symptom of this design, and the fix (batching) treats the symptom. There is no in-process cache keyed on file mtime.
- `searchNotes` still does a **full `listNotes` directory walk on every query** (`notes.ts:252`) even when the index is warm, to compute `uncovered`. At 300k notes that is a 300k-entry readdir per search.
- Priming floor logic (`query.ts:441-465`) is well-reasoned and tested. But note the ablation result: **priming is the whole engine** (15/18 → 1/18 without it), and the eval seeds the session buffer with the *target note itself* (`eval-retrieval.mjs:61-62`, `benchmark-baselines.mjs:174-175`). The benchmark therefore mostly measures "does a note you already read this session rank #1 from its MOC" — see §6.
- `fallback.ts:200` default 300ms budget is sensible; the timeout path is tested.

### Cross-process state sharing (MCP server ↔ Obsidian plugin) — workable, polling-based, no contract versioning

Plugin polls files every 2s (`PrimedWatcher.ts:3`, `ActivationSocketWatcher.ts:3`, `GraphMetadataWatcher.ts:3`), uses `fs.watch` with polling fallback for weights. It reads `LinkWeightsFile` etc. via *type imports only* and has its own copy of `liveWeight` (`render-core/ForceSim.ts:24`) — decay math is duplicated and can drift from `query.ts:318`. File `version` fields exist but no reader checks them.

### Activation socket — clever, but insecure and racy

`activationSocket.ts:510` binds `ws` on an ephemeral port with **no host** → listens on `::` (all interfaces), **no auth**, broadcasts note paths and traversal events in plaintext JSON to anyone who connects. Registration file `activation-sockets/{instance}.json` holds `{port,pid}`; the plugin connects to `ws://127.0.0.1:{port}` (`ActivationSocketWatcher.ts:79`). A stale registration whose port has been reused by another process gets a connection that never closes → the plugin will treat it as live. Startup blocks on socket bind before the MCP transport connects (`index.ts:31`) — a bind failure kills the server even though the socket is optional.

## 3. Code quality & tech debt

Overall: code is unusually well-commented, consistently structured, `strict` TS, no `any` sprawl. Debt is concentrated in I/O robustness and validation, not style.

- **No input validation beyond `z.string()`** for every note path argument (`tools.ts:57,88,180,247,269-270,319,345,385,422`). No vault-root containment check anywhere in `notes.ts:31 toFilePath` or `notes.ts:124 listNotes`.
- **Frontmatter parser is not YAML** (`frontmatter.ts:325-402`): only `key: scalar` and `key: [a, b]`. Obsidian's default block lists (`aliases:\n  - x`), nested maps, multi-line strings, and `tags:\n  - x` are **destroyed on any `update_note`** because `tools.ts:374` re-serializes `existing.frontmatter`. Confirmed empirically (§0). This is a data-loss bug for any vault not authored solely by this tool.
- **Duplicated logic**: `escapeRegExp` in `notes.ts:115` and `autolink.ts:126`; `daysSinceDayKey` in `compactor.ts:26` and `consolidation.ts:7`; `loadFs()` copied in 4 plugin files; edge-key construction `[a,b].sort().join("|")` in `compactor.ts:17`, `query.ts:508`, `NeuralGraphView.ts:256`, `desktop-app/main.ts:159`; decay formula duplicated in `render-core/ForceSim.ts:24`.
- **Autolink is O(N) file reads per write with unbounded concurrency** (`autolink.ts:397-409` `Promise.all` over every other note). This is the same EMFILE pattern already fixed elsewhere (`adapters.ts:300`). Every `create_note`/`update_note` at 300k notes would open 300k files at once.
- **Autolink correctness**: matches any 4+ char title as a word anywhere in the body (`autolink.ts:419-423`) and inserts `[[title]]` — a note titled "Index" or "Plan" will be auto-linked into nearly everything; ambiguous titles (which `structuralLinks.ts:45` deliberately refuses to resolve) are linked by bare title, producing ambiguous wikilinks.
- **Dead/vestigial code**: `EventType "decay"` never emitted (`types.ts:1`, acknowledged `usageReport.ts:256`); `DEFAULT_REINFORCE_BOOST` doc refers to a removed tool (`index.ts:62-74`); `compact_weights` description mentions `reinforce_link` (`tools.ts:300`); `SearchLogEntry.useWeights` logged but never read; `render-core/Clustering.ts` label-propagation fallback largely superseded by server-side Louvain; `bin/vnl-compact.js`/`vnl-nightly.js` duplicate `nightlyScheduler.ts` step-by-step instead of calling it.
- **Version drift**: `index.ts:47` hardcodes server version `"0.0.0"` while `package.json` is `0.1.0`; plugin `manifest.json`/`package.json` at `0.0.0`.
- **Error handling in tool handlers**: zero try/catch in `tools.ts`; any fs error (EACCES, EBUSY from OneDrive lock, malformed JSON in a data file) surfaces as a raw MCP error with a Windows path in the message. `loadWeights`/`loadStructuralIndex`/`loadContentIndex` (`query.ts:285`, `structuralLinks.ts:72`, `contentIndex.ts:174`) rethrow on anything but ENOENT — a corrupted 8MB `content-index.json` makes *every* `search_notes` call fail until the nightly rewrites it.
- **Logging**: none in core/mcp-server except the fatal env check (`index.ts:22`). No debug/trace flag, no latency logging outside `retrieval/*.jsonl`. Plugin uses `console.log` (`NightlyScheduler.ts:61`).
- **Config sprawl**: ~12 `DEFAULT_*_CONFIG` constants plus module-private tuning constants (`query.ts:278-283`, `notes.ts:13-23,206-209`, `fallback.ts:187-200`, `autolink.ts:6`) — none overridable by the user/env; the plugin's `decayHalfLifeDays` setting is a display-only mirror that can silently disagree with core.
- **Windows/path**: `toNotePath` correctly normalizes `sep` (`notes.ts:37`). But plugin builds paths with string concatenation `${basePath}/.vault-neural-links/...` (`NeuralGraphView.ts:100-137`) — works on Windows only because Node tolerates mixed separators. `structuralLinks.ts:39` lower-cases targets for resolution, so two notes differing only in case (legal on Linux, impossible on Windows/macOS default) collide.
- **Hardcoded paths/secrets**: none found in `src/`. `.claude/settings.local.json` is committed-adjacent (not in git per status) — fine.

## 4. Security review

**Critical — path traversal in every path-taking MCP tool.** `notes.ts:31-34` `toFilePath = join(vaultPath, notePath + ".md")` with no `resolve`/prefix check. Confirmed via the real MCP protocol: `read_note {path:"../outside/evil"}` returned a file outside the vault; `list_notes {folder:"../outside"}` enumerated a sibling directory; `writeNote(vault, "../outside/evil")` created a file outside the vault. Impact: any prompt-injected content (a note, a web page the agent read) can instruct the agent to **read any `.md` file** and **write/overwrite any path ending in `.md`** anywhere the user can, plus `create_note` will `mkdir -p` arbitrary directories (`notes.ts:70`). Also applies to `get_edge_weight`/`activate` (only `.md` reads via `readNoteType`/`readSupersession`, lower impact) and to desktop-app IPC handlers which pass `notePath` straight through (`main.ts:331-366`).
Fix: one helper `resolveInsideVault(vaultPath, notePath)` — `path.resolve`, reject if not `startsWith(resolve(vaultPath) + sep)`, reject absolute paths, reject `..` segments, reject `.vault-neural-links/` and `.obsidian/` prefixes — used by `toFilePath`, `listNotes`, `readNoteType`, `readSupersession`. Add zod `.refine` in `tools.ts`.

**High — activation WebSocket bound to all interfaces, unauthenticated.** `activationSocket.ts:510`. On a laptop on café Wi-Fi, anyone on the LAN can connect to the ephemeral port and receive the user's note titles/paths as they are traversed (client-confidential project names are visible in the eval set). Fix: `new WebSocketServer({ host: "127.0.0.1", port: 0 })` (one line) and optionally a random token in the registration file that clients must send first.

**Medium — plaintext access token on disk.** `accountSession.ts:120-136` writes `~/.vault-neural-links/account-session.json` containing `accessToken` in plaintext, `0644`-equivalent, no `mode`. The design doc argues it's bounded by TTL; the mock IdP TTL is 5 minutes (`mockIdp.ts:11`), but the real IdP TTL is undecided, and nothing enforces a short TTL on the reader side. The refresh token *is* protected via `safeStorage` (`auth.ts:521-528`) — good — but falls back to plaintext with only a `console.error` (`auth.ts:523-526`). Also: any local process can *forge* this file to make the plugin show "logged in" (`accountAuth.ts:120-123` trusts presence + expiry only, acknowledged in comments). Nothing is gated on it yet, so exposure today is informational.

**Medium — desktop renderer XSS surface.** `renderer.ts:227,267,350` interpolate note paths/`matched` into `innerHTML`; `renderer/index.html` has no CSP `<meta>`. A note path like `<img src=x onerror=...>.md` is unusual but possible; `contextIsolation: true` + `nodeIntegration: false` (`main.ts:176-177`) limits blast radius to the renderer.

**Low** — `mockIdp.ts:303-306` reflects unescaped query params into HTML (dev-only). `oauth.ts:95` reflects `error` param into HTML. `qs` advisory unreachable (stdio transport). MCP server prints full Windows paths in error messages (info leak to the model, minor).

**Not an issue**: no secrets in repo; `.gitignore` covers runtime data; `ws` and `zod` current.

## 5. Performance & scale

**What was actually verified at 300k notes** (per code comments and STATUS): `adapters.ts` batched `listNodes` (~17s), `buildStructuralIndex` (~13s, ~150MB RSS), and `searchNotes` with the content index (336s → 2.1s selective; 206s repetitive vocab). All on a **synthetic corpus with tiny notes and a small vocabulary**.

**What was not verified and will not hold** on a real-vocabulary corpus:

- **Content index size**: 8.5MB for 471 real notes (18KB/note; 20,886 tokens). Linear extrapolation → **~5.2GB at 300k notes**, above V8's max string length (~512MB) — `JSON.parse` in `loadContentIndex` (`contentIndex.ts:176-177`) will throw `Invalid string length` / `ERR_STRING_TOO_LONG`, and because the loader rethrows non-ENOENT errors, **every `search_notes` call fails**. Even at 20k real notes (~360MB) the index is parsed from disk on **every query** (`notes.ts:267`) — hundreds of ms and a transient 1GB+ heap spike per search. The design (postings as `Record<token, string[]>` of full paths, no path dictionary, no shard, no mtime cache) is the problem, not the constant.
- **structural-links.json** extrapolates to ~137MB; **it is loaded and parsed on every `computeLiveNeighborWeights` call** (`query.ts:415`), i.e. many times per `activate`. Retrieval at 300k was never measured; it would be seconds per hop.
- **link-weights.json** is scanned O(E) per neighbor lookup (`query.ts:398`); fine at 122 edges, not at 10^5–10^6.
- **autolink on write**: reads every note in the vault with unbounded concurrency (`autolink.ts:397`) — `create_note` at 300k notes will EMFILE/OOM exactly like AIBRAIN-132 did for search.
- **Nightly pipeline runs on Obsidian's main thread** (`NightlyScheduler.ts:8-10` acknowledges) — PageRank (50 iters) + Louvain over 300k nodes will freeze the Obsidian UI for tens of seconds to minutes.
- **`mostRecentNotes`** (`notes.ts:163-171`) stats every note with an unbounded `Promise.all` — the "cheap recency tier" is O(N) unbounded fs calls.

**Cold start**: MCP `initialize` answered in ~1.5s (node boot + import + ws bind + registration write). Startup does **not** run compaction or the nightly (`index.ts:33-36`) — good. No index is loaded until first tool call.

**Memory**: `link-weights.json` at the real vault is 45KB — negligible. The real memory risk is `content-index.json` (above) and the eval at 300k was never about memory of retrieval.

**Honest claim check**: README says "verified against a 300,000-note vault" for "search and retrieval". Only *search* on a synthetic fixture was verified; `activate`/`get_weighted_neighbors`/`create_note` at that scale were not, and the content-index design cannot reach that scale with real note bodies. PLAN §5 "Verified at 300k-note scale: 336s → 2.1s on a selective query" is accurate but narrow.

## Bottom line

The retrieval *engine* is thoughtfully designed, well-commented, and unit-tested; the mechanism-level claims (decay, priming, consolidation, PageRank, Louvain, spreading activation, fallback) are all real and behave as documented. What is **not** true yet: that it is safe to expose to an LLM (path traversal, open socket), that it is safe to point at an existing Obsidian vault (frontmatter destruction on update), that it scales to 300k notes for anything beyond a synthetic search benchmark, or that the 15/18 benchmark demonstrates the Hebbian-weight thesis (it demonstrates priming). Fixing risks 1–5 is roughly two engineer-days and should precede the first npm publish; risks 6–8 determine whether the product's scale and "gets better with use" claims can be stated honestly.
